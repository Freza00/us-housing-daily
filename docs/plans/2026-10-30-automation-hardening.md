## 本期版本和恢复事实源

建议以 `kind + period_key + cutoff_upper + revision` 标识某一期的某个版本。普通重试保持这四项不变；新证据、重新编辑或主动修订生成新 revision，旧版可追溯。固定版本只补齐缺失阶段，不重新 enrich 或覆盖已冻结输入。新发现原料继续按逐源水位保存，等待新修订或下一期处理，不因冻结而丢弃。

新增 `state/issues/<kind>/<period>/<revision>/` 时先约定职责：`input.json` 保存稳定 ID、正文版本及实际提供给模型的证据；`decisions.json` 保存通过契约的编辑决策；`cards.json` 保存逐稿校验结果；`metadata.json` 的摘要和主线绑定实际入选集合；`release.json` 保存完整已校验刊物。小型 manifest 记录文件散列、代码／提示词／校验规则版本、失败阶段和尝试记录。文件格式为实施建议，正式接口在实施检查点 B 中定稿。

ready 阶段同时保存可独立发布的完整候选包、生成文件前置条件和本期 state 增量，确保推送失败后的恢复不依赖已经消失的 runner 工作目录；它不能作为覆盖最新共享 state 的整包快照。

本地阶段目录加入 `.gitignore`，发布改用明确 allowlist，避免现有 `git add state/` 把未出版卡片和全部中间阶段带入 main。正式提交只含本期刊物、索引／首页及约定的 seen、采集检查点、原始快照和实际输入；阶段附件和诊断走独立保存路径。

跨 runner 首版优先使用已有 GitHub artifact 能力，在输入就绪、编辑通过、卡片／摘要校验等阶段边界保存明确的本期阶段附件，manifest 记录可信工作流／run／artifact 标识和散列，恢复显式下载并验证。仅接收指定仓库及受信任分支的预期工作流产物；实施时按最小需要加入 actions:read，保留期须覆盖恢复窗口及首轮验收。中间阶段不推 main，避免每个阶段触发 Vercel 部署；正式发布继续提交当前 data/state 约定范围。Actions cache 保留作加速，原始快照和已提交 state 保留作长期追溯。

附件保存必须有超时和有限重试，未经确认保存成功的阶段不能标作可跨运行恢复。保存缺失、过期、散列或校验版本不一致时，明确报告恢复不可用，不静默改读最新网页重新选稿。已有完整合格候选仍可走最终 Git 发布路径；需要重新生成时显式建立新版本并记录原因。不得把阶段持久化故障扩大成无限重试或新增无限模型调用。

远端附件保存失败时，当前 runner 可以在预算内继续使用已校验的本地阶段完成候选并发布，但必须记录跨运行恢复尚不可用；不能把附件故障变成已合格成稿的硬性发布前置条件。本地关键文件写入失败仍应停止，避免水位与原料不一致。

恢复附件只提供本期输入和阶段结果，不能整包覆盖最新共享 state。逐源水位和 observed 保持单调，pending 按材料指纹消费，seen 按实际已刊版本维护，不能对同日修订一律做简单并集。恢复旧版仍先读取当前远端状态，不回退其他期刊已经推进的水位或清掉新原料。

## 交付状态与内容质量分别判断

保留三种独立含义：来源覆盖 complete／degraded；内容契约 passed／failed；交付 ready／pushed／online_verified。旧字段在迁移期提供明确兼容映射，网页仍能解释来源缺口。只有内容通过校验的候选能进入 ready，覆盖不完整不会自动变成未生成，推送成功也不会自动变成线上确认。

验证分离不要求正常情况下增加模型请求：编辑一次、写稿一次，写稿仍可同时返回卡片和摘要；程序分别验收和保存，只有失败部分才进入有界修复。原文、数字、连续引文和全体 selected 的覆盖要求继续生效，P0 不自动删除失败卡片。

局部纠正共享该 writer 阶段的请求次数和时间预算，多个坏卡合并成一批指定 ID 修复，不给每张卡各自额外重试 3 次。跨运行计数与失败原因一并保存，普通补偿不能重置该期的限额。

```mermaid
flowchart LR
  A[冻结输入] --> B[编辑通过]
  B --> C[逐卡通过]
  C --> D[摘要通过]
  D --> E[候选就绪]
  E --> F[Git 推送确认]
  F --> G[线上内容确认]
```

发布器绑定候选的期号、revision、cutoff 和内容散列，确认远端 main 包含目标提交后，再轮询部署并读取生产首页、latest 和本期归档。不同内容、旧期、非 200 或超时均不标成功。与更新远端发生冲突时，仅对本轮生成文件执行有界的安全重试，保护新代码、更新期刊和其他种类的 state；不强推、不改写历史，不回退水位。已存在更高版本时停止覆盖。

已推送但部署失败必须调用经过验证的 Vercel redeploy 入口，保留同版候选，重复 push 同一提交不能创建新的部署。官方提供 [redeploy CLI](https://vercel.com/docs/cli/redeploy) 和 [Deploy Hook](https://vercel.com/docs/deploy-hooks) 等能力；建议优先验证绑定目标 deployment／commit 的接口或 CLI。此前凭据验证未通过，本轮没有可用自动 redeploy 权限的证据，因此 C 的自动恢复上线前必须完成能力验收；尚无权限时只能监测并告警，不能声称已自动自愈。若采用 Hook，其地址按密钥保存，并核对最终部署的提交，不能假定分支始终停在原候选上。

线上确认凭据保存为独立操作记录，绑定候选内容散列和已推送提交，不回写同一生产 JSON，避免确认状态又改变候选、触发新部署的循环。凭据保存失败须报告监控记录不完整；观察器可重新读取线上核验，不因此重启生成。

日／周／月当前共享水位及 Git 写入，首版保留受控串行写入。观察者不进入该长任务并发组；按“期号＋版本”合并重复恢复请求。不能只把三类工作流拆组后并发写共享状态；也不以积压全部补偿任务替代出刊机制。

同一期去重仍不能消除不同类型任务互相替换 pending 的风险。首版让独立观察器按所有到期期刊检查缺刊并作有界补偿；后续如仍存在竞争，再引入共同的到期判断入口和日报／周报优先级，不把共享水位并发写入作为默认解法。

## 截止检查与降级政策

09:00 前线上可读沿用现有工作日目标。建议观察器在 08:00 检查进度，08:15 前结合剩余阶段作完整恢复决策，08:40 后优先处理已就绪候选的发布／核验，09:00 核对结果并通知失约。现有 job 上限为 20 分钟，08:45 才重启完整生成再部署不足以保障 09:00，因此时点需结合排队、阶段耗时和实际套餐精度校准。每次外部调用前检查剩余预算，给推送、部署和线上校验留余量。

09:00 是服务目标，超过时刻即记为失约并告警。工作日仍可按已记录的剩余次数和费用预算继续有界迟到恢复，不能因错过目标而永不出刊，也不能每次 cron 重置预算无限调用。已就绪候选始终优先仅恢复交付；迟到版本不能覆盖更新的期号／修订。

固定期号恢复仍遵守现有北京时间周末守卫及三类期刊截止点。延迟任务不得把重试时刻作为新 cutoff，也不得让旧期恢复覆盖较新的 latest。周末观察可以只读发现问题，生产采集和发布继续按现行守卫退出。

独立观察器需在 GitHub 生成调度未启动时仍能运行；可基于用户已有独立运行环境确认承载。Vercel cron 的实际套餐、注册及调用健康须只读核实。即使外部 cron 能发送 GitHub dispatch，也不能绕过 GitHub 执行器整体故障；如果用户要求此类故障下也必须出刊，需要另定备用执行器及投入。

自动少稿出刊须先确定最低可用内容及关键主题要求。本轮不凭空设置最低条数，也不能把任意一张合格卡片当作合格日报；P0 维持全体 selected 校验通过才可发布。P1 若获准开放精简版，只使用当期或具有可追溯积压资格、并通过数字和连续引文检查的卡片，不按栏目凑数。摘要只能引用最终保留集合；无法修复时可改为确定性抽取已通过的卡片摘要，或省略速读区，并明确标记精简版，具体规则待用户确认。

以下情况保留最后可读版本并告警，不能伪造当天日报：无合格卡片、稳定 ID／引用关系无法确认、截稿或版本错配、共享状态不一致、完整刊物校验失败。个别关键事件无法核实时是否允许精简版，单独确定政策；不默认放宽关键事实校验。来源补查可继续保存新原料，已刊 degraded 的补全走有界修订流程，不反复覆盖同一个版本。
